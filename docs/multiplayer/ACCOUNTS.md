# Accounts, social play and deployment

Offline play needs no account or backend. Online play requires Supabase Auth/Postgres **and** the persistent authoritative Node game server. Installing a connector or deploying the static frontend does not deploy either service. No Blackout cloud project or public game-server endpoint has been configured by this change.

## Local setup (Node 24+, Docker Desktop)

```sh
npm install
npx supabase start
npm run accounts:env
npm run dev
```

The migration in `supabase/migrations/` is applied to the local stack on first start. `accounts:env` reads only the local stack and writes ignored `.env.test` and, if absent, `.env`. Existing `.env` is preserved. Do not copy example placeholders over this generated configuration. Restart both processes after changing environment values.

Frontend: http://127.0.0.1:5173 . Auth/Data API: http://127.0.0.1:54321 . Game server: ws://127.0.0.1:3001/ws . Local email capture: http://127.0.0.1:54324 . Separate process commands: `npm run dev:client` and `npm run server:dev`.

Use distinct accounts in separate browser profiles/devices. On one machine, `127.0.0.1:5173` and `localhost:5173` provide separate browser storage while using the same server. Sign up, set a unique username, then create/join or find a friend by exact username/UID. Local email confirmation is disabled for testing; enable it in production. Recovery messages go to the local mail capture, not the Internet.

```sh
npm test
npm run test:network  # mechanics/security socket regression; explicit constructor-only guest test mode
npm run test:accounts # real local Auth users, RLS, social, invitations, authoritative 1v1, 2v2/4v4 capacities
npm run typecheck
npm run server:build
```

`test:accounts` creates and removes its own disposable local accounts. It refuses hosted API URLs. `/tests/network-browser.html` requires two existing test account logins with completed profiles; its scripted input is automation, not human play. These fixtures are not production entry points.

## Production: three separate services

1. Create/select a **Blackout-specific** Supabase project. Do not reuse unrelated application databases. Apply the versioned migration to it using the Supabase migration workflow (`supabase link --project-ref YOUR_PROJECT`, inspect pending migrations, then `supabase db push`). Review with `supabase db advisors --linked --type security`. The CLI may require authentication. Do not reset a hosted database.
2. Configure Supabase Auth: allow email/password signup, enable confirmation, set the site URL to the actual HTTPS frontend origin and allow the precise frontend redirect URLs (including the deployment base path and recovery query). Configure supported production SMTP delivery and Auth rate limits. No custom password table is used.
3. Deploy the Node server to a service that supports persistent WebSockets. Supply server-only `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, exact comma-separated `ALLOWED_ORIGINS`, `HOST=0.0.0.0`, platform `PORT`, and `NODE_ENV=production`. Supply a writable persistent `RESULT_OUTBOX_PATH` (Docker default `/app/data/match-outbox.json`, mount a volume there). Never log or bundle the server secret.
4. Terminate TLS at the host/proxy. Route `/ws` with WebSocket upgrades and `/health` and `/ready` over HTTPS. `server/Caddyfile.example` is a placeholder configuration. Set proxy idle timeout above the ten-second socket heartbeat. `/health` is liveness; `/ready` returns 503 when identity/database/outbox readiness fails. Allow readiness CORS only for the actual frontend origin.
5. Build/deploy the static frontend with **public** `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, and `VITE_MULTIPLAYER_URL=wss://YOUR_REAL_SERVER/ws`. Rebuild after changing these; changing server runtime variables cannot update an old static bundle. Production builds reject loopback/insecure endpoints and obvious secret-key exposure. Missing multiplayer configuration produces an explicit unavailable state, never a same-host guess.
6. Verify health/readiness through the public endpoint, then connect two independent authenticated clients and play a complete match. **Public multiplayer is unverified until this succeeds.** No server URL is invented here.

For an intentionally offline-only production build, unset all three public values before `npm run build`. Development credentials generated by `accounts:env` are loopback-only and deliberately rejected by production configuration checks.

The local Docker configuration is development-only. In-memory rooms and reconnect sessions **do not survive server restart**. Profiles/social data/statistics survive in Postgres; the persistent result outbox retries already-finished summaries after a server restart. One server instance owns a room; this is not a horizontally distributed room service.

## Identity and authorization

- Supabase owns passwords, sessions and account recovery. The server verifies access tokens against Auth (`getUser`) and loads trusted profile data. Access tokens travel in handshake/refresh message bodies, never URLs. Session expiry closes the connection; reconnect needs both a valid account token and that actor's random reconnect secret. Invalid identity cannot claim another slot.
- Internal account UUID and database-generated `BO-` public UID are immutable. UID is public lookup data, not authentication. Public search never returns emails. Usernames are case-insensitively unique, 3–20 letters/digits/underscores, beginning with a letter; renames are limited to once per 30 days. Display name/avatar can change; current room names update on the next join.
- RLS is enabled on every application table. Clients have no table mutation grants. Bounded RPCs derive the actor from `auth.uid()` and authorize each action. Private-schema helpers have revoked public execution and fixed empty search paths. The public RPCs are deliberate authenticated APIs; their security-definer bodies perform ownership checks. Only the service role may create/consume room invitations or record results.
- Canonical friendship pairs, uniqueness constraints, row/advisory locks serialize crossed requests, blocks and invite acceptance. Crossed requests become one accepted friendship. Only recipients accept/decline; only senders cancel. Blocking revokes pending invites and removes friendship. Search/request/invite limits are 30/20/15 per minute per account; other profile/presence/read operations are bounded too.
- Friend presence is advisory: one random per-page session, heartbeat every 20 seconds, expiry after 75 seconds. One tab signing out removes only its own heartbeat. No room code or join credential appears in presence or public profiles. Background-browser throttling can delay advisory presence.
- Invitations are recipient-bound, two minutes, accepted only by the authenticated recipient. The game server checks current friendship, blocks, live room instance, lobby state and capacity. Active-match arrivals are rejected. Acceptance never silently leaves another match. Room codes/links remain usable by signed-in players, including non-friends. Pending code links survive sign-in redirects in session storage.
- Hosts may move lobby players only where capacity permits, clearing the moved player's ready state. Team changes do not alter immutable identity. Active roster/rules remain frozen. Bot fill is explicit and labeled.

## Trusted statistics

Only the authoritative server emits a finished-match UUID and participants' scores. The service-role RPC inserts match/results and updates counters in one transaction. Retrying the identical UUID/payload does not increment twice; conflicting payloads fail. Browser table writes and result RPC execution are denied.

Completed human-only online matches count matches, wins/losses/draws, eliminations and deaths. Bot-fill matches are practice. Matches with departed actors or abandonment forfeits are recorded separately and **do not** count as ordinary completed results. Offline practice never reaches this API. A server crash before match completion creates no completed result. Queued finished summaries require a persistent outbox volume; unreadable/full outboxes disable readiness. Keep the server secret restricted to the game service: anyone holding it is trusted infrastructure.
